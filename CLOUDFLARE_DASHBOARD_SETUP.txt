CLOUDFLARE DASHBOARD SETUP FOR FLUE + SVELTEKIT
================================================

This checklist configures the Cloudflare account resources required by this
repository.

Repository resource names
-------------------------

Web Worker:
  flue-sveltekit-demo

Agent Worker:
  flue-sveltekit-agent

D1 database:
  flue-sveltekit-demo-threads

D1 database ID currently expected by wrangler.jsonc:
  9edccc92-e765-4277-b286-e9225add7bde

Web-to-agent service binding:
  Variable name: FLUE_AGENT
  Target Worker: flue-sveltekit-agent

Web-to-D1 binding:
  Variable name: THREADS_DB
  Database: flue-sveltekit-demo-threads

Agent Cloudflare AI binding:
  Variable name: AI

AI Gateway ID:
  flue-sveltekit-demo

Choose this value before starting:
  APP_HOSTNAME=<a hostname in an active Cloudflare zone, such as chat.example.com>


1. ACCOUNT PREREQUISITES
------------------------

[ ] The domain used by APP_HOSTNAME is an active zone in the same Cloudflare
    account where the Workers will be deployed.

[ ] Cloudflare Zero Trust has been initialized for the account.

[ ] At least one Access identity provider or login method is configured for the
    people who should use the app.

[ ] Workers, D1, Durable Objects, the Cloudflare AI binding, and AI Gateway are
    available for the account. Accept any product setup prompts shown by
    Cloudflare.

All resources in this checklist must be created in the same Cloudflare account.
The FLUE_AGENT service binding cannot target a Worker in another account.


2. CREATE OR VERIFY THE D1 DATABASE
-----------------------------------

Dashboard path:
  Cloudflare Dashboard > Storage & databases > D1 SQL database

[ ] Look for a database named:
      flue-sveltekit-demo-threads

[ ] If it already exists, open it and confirm its database ID is:
      9edccc92-e765-4277-b286-e9225add7bde

[ ] If the database does not exist, select Create Database and use the exact
    name:
      flue-sveltekit-demo-threads

IMPORTANT:
If Cloudflare creates a different database ID, replace database_id in the root
wrangler.jsonc before deploying. Do not leave wrangler.jsonc pointing at a
database from a different account.

The dashboard creates the database, but it does not apply this repository's
migrations automatically. After authenticating Wrangler, run from the repo
root:

  pnpm db:migrate:remote

The remote database must contain the users and threads tables from all files in
migrations/.


3. CREATE OR VERIFY THE AI GATEWAY
----------------------------------

Dashboard path:
  Cloudflare Dashboard > AI > AI Gateway

[ ] Create a gateway with the exact ID/name:
      flue-sveltekit-demo

Use this dedicated gateway rather than default so its rate and spend policies
cannot affect unrelated applications.

[ ] Leave provider credentials empty. This application calls
    @cf/moonshotai/kimi-k2.6 through the Workers AI binding, so it does not
    require an external model API key or Unified Billing balance.

[ ] Do not enable content logging unless an intentional retention and access
    policy has been approved. The agent also sends collectLog=false.

[ ] Enable gateway rate limiting with a sliding limit of 60 requests per minute.

[ ] Add a global spend limit of $5 per rolling day with the Block action. This
    is intentionally small because this repository is a test project.

No model is selected in the dashboard. The agent profiles select
@cf/moonshotai/kimi-k2.6 with low reasoning in source code. Testing usage is
covered by Workers AI's daily free allocation until that allowance is exhausted.


4. DEPLOY AND VERIFY THE PRIVATE AGENT WORKER
---------------------------------------------

Deploy the agent first because the web Worker has a service binding that targets
it:

  pnpm agent:deploy

Dashboard path:
  Cloudflare Dashboard > Workers & Pages > flue-sveltekit-agent

Verify the following:

[ ] Settings > Domains & Routes:
      workers.dev is Disabled
      Preview URLs are Disabled
      No custom domain or public route is attached

[ ] Settings > Bindings:
      AI binding named AI exists

[ ] Settings > Variables and Secrets:
      AI_GATEWAY_ID has the value flue-sveltekit-demo

[ ] Durable Object bindings/classes generated by Flue are present. The current
    migration chain ends with:
      FlueRegistry
      FlueResearchAgentAgent

[ ] Observability / Workers Logs is enabled.

Do not manually create, rename, or delete the Flue Durable Object namespaces.
The migrations in agent/wrangler.jsonc manage the class history.

The agent Worker is intentionally private. It should be reachable only through
the FLUE_AGENT service binding on the web Worker.


5. DEPLOY THE WEB WORKER
------------------------

After the agent Worker exists and the D1 migrations have been applied, deploy
the web Worker:

  pnpm deploy

Dashboard path:
  Cloudflare Dashboard > Workers & Pages > flue-sveltekit-demo

Verify Settings > Bindings:

[ ] D1 binding:
      Variable name: THREADS_DB
      Database: flue-sveltekit-demo-threads

[ ] Service binding:
      Variable name: FLUE_AGENT
      Service: flue-sveltekit-agent

[ ] Rate Limiting binding:
      Variable name: AI_SUBMISSION_RATE_LIMITER
      Limit: 10 requests per 60 seconds

[ ] Static asset binding ASSETS is present after the SvelteKit deployment.

[ ] Observability / Workers Logs is enabled.

If the service binding is missing, do not replace it with a public agent URL.
The binding must point to the exact Worker name flue-sveltekit-agent.


6. CREATE THE CLOUDFLARE ACCESS APPLICATION
-------------------------------------------

Create Access protection before publishing the custom hostname.

Dashboard path:
  Zero Trust > Access controls > Applications

[ ] Select Create new application.

[ ] Select Self-hosted and private.

[ ] Select Add public hostname.

[ ] Set the public hostname to APP_HOSTNAME. Protect the entire hostname, not
    only /api or another path.

[ ] Add an Allow policy containing only the intended users, email addresses,
    groups, or identity-provider rules.

Access applications deny by default, but the application needs at least one
matching Allow policy for anyone to sign in.

[ ] Select the identity provider or login method users will use.

[ ] If only one identity provider is available, optionally enable instant
    authentication.

[ ] Choose an appropriate session duration.

[ ] Create the Access application.

After creation:

[ ] Open Configure for the application.

[ ] Open Additional settings.

[ ] Copy the Application Audience (AUD) Tag. This becomes CF_ACCESS_AUD.

[ ] Record the Zero Trust team domain. It has this form:
      https://<team-name>.cloudflareaccess.com

    This becomes CF_ACCESS_TEAM_DOMAIN. Include https:// and do not add a path.

The web Worker validates the Cf-Access-Jwt-Assertion header itself. It checks
the signature, exact issuer, RS256 algorithm, application audience, subject,
and optional email. A missing or invalid token returns 403 Forbidden.


7. ADD THE ACCESS VALUES TO THE WEB WORKER
------------------------------------------

Dashboard path:
  Workers & Pages > flue-sveltekit-demo > Settings > Variables and Secrets

Add these two values to the production environment:

[ ] Name:
      CF_ACCESS_TEAM_DOMAIN
    Value:
      https://<team-name>.cloudflareaccess.com

[ ] Name:
      CF_ACCESS_AUD
    Value:
      <the Application Audience AUD Tag copied from Access>

Recommended dashboard setting:
  Store both as encrypted secrets.

These values are identifiers rather than credentials, but encrypted secrets are
preserved by Wrangler deployments. Plaintext dashboard variables can be
overwritten by Wrangler because the current root wrangler.jsonc does not set
keep_vars.

Do not add FLUE_AGENT_URL to the deployed web Worker. That value is only for the
local HTTP fallback. Production must use the FLUE_AGENT service binding.

After adding or changing either value, deploy a new Worker version if the
dashboard asks for one, and confirm the values are attached to the active
production deployment.


8. ATTACH THE CUSTOM DOMAIN TO THE WEB WORKER
---------------------------------------------

Dashboard path:
  Workers & Pages > flue-sveltekit-demo > Settings > Domains & Routes

[ ] Select Add > Custom Domain.

[ ] Enter APP_HOSTNAME, exactly matching the hostname in the Access
    application.

[ ] Select Add Custom Domain.

Cloudflare creates the required DNS record and certificate. Wait until the
custom domain reports Active before testing.

[ ] Disable the web Worker's workers.dev route.

[ ] Disable Preview URLs.

This removes alternate public entry points outside the intended Access
hostname. The application validates Access JWTs and fails closed, but unused
public routes should still be removed.

The root wrangler.jsonc sets workers_dev=false and preview_urls=false so
Wrangler deployments preserve both restrictions.

Agent Worker: flue-sveltekit-agent

[ ] workers.dev Disabled
[ ] Preview URLs Disabled
[ ] No custom domain
[ ] AI binding named AI
[ ] AI_GATEWAY_ID=flue-sveltekit-demo
[ ] Flue Durable Object bindings/classes present
[ ] Workers Logs enabled

Web Worker: flue-sveltekit-demo

[ ] APP_HOSTNAME custom domain is Active
[ ] workers.dev Disabled
[ ] Preview URLs Disabled
[ ] THREADS_DB points to flue-sveltekit-demo-threads
[ ] FLUE_AGENT points to flue-sveltekit-agent
[ ] AI_SUBMISSION_RATE_LIMITER is present
[ ] CF_ACCESS_TEAM_DOMAIN is present on the production deployment
[ ] CF_ACCESS_AUD is present on the production deployment
[ ] Workers Logs enabled

Zero Trust Access

[ ] Self-hosted application hostname exactly matches APP_HOSTNAME
[ ] At least one intended user matches an Allow policy
[ ] Unintended users do not match an Allow policy
[ ] AUD copied into CF_ACCESS_AUD belongs to this exact Access application
[ ] Team domain copied into CF_ACCESS_TEAM_DOMAIN belongs to this account

D1

[ ] Database name and ID match wrangler.jsonc
[ ] All remote migrations have been applied
[ ] users table exists
[ ] threads table contains user_id, status, and tombstoned_at columns

AI Gateway

[ ] Gateway ID flue-sveltekit-demo exists
[ ] Gateway rate limit is 60 requests per minute using a sliding window
[ ] Global spend limit is $5 per rolling day with the Block action
[ ] @cf/moonshotai/kimi-k2.6 requests appear in gateway analytics after a test conversation
[ ] Content logging remains disabled unless explicitly approved


10. END-TO-END TEST
-------------------

1. Open https://APP_HOSTNAME in a private browser window.

2. Confirm Cloudflare Access prompts for authentication before the app loads.

3. Sign in with a user allowed by the Access policy.

4. Confirm the SvelteKit application loads without a 503 authentication
   configuration error or a 403 token validation error.

5. Create a thread and send a message.

6. Confirm a streamed response appears.

7. In D1, confirm:
     - one users row exists for the Access subject;
     - the thread row references that user through user_id;
     - D1 does not contain a second transcript.

8. In the web Worker logs, confirm the request reaches the FLUE_AGENT service
   binding without binding or authorization errors.

9. In the agent Worker logs and AI Gateway analytics, confirm an
   @cf/moonshotai/kimi-k2.6 request completes with low reasoning.

10. Confirm the following alternate URLs are unavailable:
      flue-sveltekit-agent.<account-subdomain>.workers.dev
      flue-sveltekit-demo.<account-subdomain>.workers.dev
      versioned or aliased Preview URLs for either Worker


11. COMMON FAILURE MEANINGS
---------------------------

503 "Cloudflare Access authentication is not configured."
  CF_ACCESS_TEAM_DOMAIN or CF_ACCESS_AUD is absent from the active web Worker
  deployment.

403 "Forbidden"
  Access did not add a JWT, or the token issuer, audience, signature, or subject
  does not match the configured application.

503 "The thread database is not connected."
  THREADS_DB is missing or points to the wrong D1 database.

503 "The Flue agent is not connected."
  FLUE_AGENT is missing or does not target flue-sveltekit-agent.

D1 error about a missing table or column
  The remote migrations were not fully applied.

Workers AI or gateway error
  Verify the AI binding, AI_GATEWAY_ID=flue-sveltekit-demo, gateway existence,
  remaining Workers AI daily allocation, spend-limit state, and
  @cf/moonshotai/kimi-k2.6 availability.

429 "Too many agent submissions."
  The authenticated user exceeded the Worker-side limit of 10 submissions per
  minute. Wait for the retry-after interval before trying again.

Access login succeeds but the app returns 403
  The Access application AUD or team domain copied into the web Worker does not
  match the application that protected APP_HOSTNAME.


12. NOT REQUIRED FOR THE CURRENT IMPLEMENTATION
------------------------------------------------

Do not create or configure these unless a later implementation explicitly adds
them:

  - OpenRouter, OpenAI, Anthropic, or other model API keys
  - R2 buckets
  - Queues
  - Workflows
  - AI Search
  - Browser Rendering / Browser Run
  - Cloudflare Sandbox
  - Analytics Engine datasets
  - Context7 or Firecrawl credentials


13. SAFE DEPLOYMENT ORDER FOR FUTURE RELEASES
---------------------------------------------

1. Deploy flue-sveltekit-agent.
2. Apply remote D1 migrations.
3. Deploy flue-sveltekit-demo.
4. Verify the web Worker still has the two Access secrets.
5. Verify both service and D1 bindings.
6. Verify workers.dev and Preview URLs remain disabled.
7. Run the end-to-end test through APP_HOSTNAME.
